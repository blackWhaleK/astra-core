## M2-FINISH-01 · 首期计时简化建议

本节是根据用户“这一期简单点”的偏好提出的新建议，尚待判断。此前累计 RUNNING 时间、单次澄清独立计时等方案暂缓，综合稿中相关参数和 V05、V06、V22 等预期应随最终取舍调整。

建议保留一个每段连续处理的超时限制。开始执行或接受澄清回复进入 RUNNING 时开始本段计时，范围包含本段节点处理、依赖等待及有限重试。达到时限时若仍处于本段 RUNNING，则按执行超时进入 FAILED。

进入 WAITING_INPUT 后结束本段计时，等待用户沿用已有的 8 小时会话空闲有效期。有效回复重新开始一段处理并重新计时。旧处理段的超时事件只对原段有效。缓存过期采用现有“会话已失效，请重新发起”处理，具体终态按可用记录判断。

单次模型、工具等依赖调用仍配置超时，循环和 Agent 沿用有限轮次约束。具体时长在实施配置时确定。本建议使计时范围限于每段连续处理，跨澄清的总累计时间留待后续确有需要时设计。

### 二、运行规则补充

#### M2-FINISH-05 · 启动校验与推进

已有 P-004 要求 YAML 加载校验、参数映射及节点执行，§4.2.3 要求启动校验通过后创建执行。

建议在场景版本可调用前校验节点及组件引用、必填配置、输入输出映射、分支去向、并行汇聚配对和循环边界。首期用显式 LOOP 表达循环。错误版本保持不可调用，并返回可定位到场景版本和节点的原因。运行时输入缺失或类型不符，按场景已定义的业务提示或错误规则处理。

建议条件分支返回一个明确分支键，未匹配时执行配置的默认分支；缺少默认分支则以编排错误结束为 FAILED。完成须取得符合场景输出契约的结果。RUNNING 时，若既无可运行节点，也无在途调用、已安排的重试等有效唤醒事件，且尚未满足完成条件，则以无法推进结束为 FAILED。

M1 每次新建 Execution 时提供选定版本，M2 固定该版本和本次有效参数。澄清续接继续使用原版本及参数。新执行如何选择版本由 M1 细化。

#### M2-FINISH-01 · 时限与澄清

建议执行时限按处于 RUNNING 的实际累计时长计量，包含排队、依赖等待、重试间隔和节点处理。并行节点同时运行的时间按经过时间计算。进入 WAITING_INPUT 时暂停该计时，建立本次等待截止时间。有效回复使执行回到 RUNNING 后，继续使用剩余执行时间。

同一等待期间，归属与追问关联正确但信息仍不足的回复可保存并继续提示，保持 WAITING_INPUT 和原等待截止时间。重复回复和错误关联回复维持既有等待状态。运行后再次需要澄清时，建立新的追问标识和等待截止时间。

建议每次超时事件关联相应执行及本次计时范围。生效前核对状态和截止时间，已续接的旧等待计时事件失效。处理节点结果、回复和下一次分发前均检查适用时限，避免定时事件延迟导致超时后继续推进。适用时限到达时进入 FAILED，并采用统一收尾规则。

有限执行时限和单次等待时限结合 8 小时缓存规则约束资源占用。缓存先失效时采用会话失效处理。具体时限数值待确定。

#### M2-FINISH-02 · 并行与汇聚

建议首期采用所有本次实际启动分支均为必需分支的规则。所有必需分支成功后触发一次汇聚，结果按分支标识映射。条件选择中未启动的路径不计入等待集合。空分发按编排错误处理。

并行分支的正常结束先交回该分支结果，Execution 的成功结束须满足整个场景的完成条件。建议把执行级 RETURN 安排在必需并行段汇聚之后，避免一个分支提前结束整次执行。

任一必需分支发生不可重试错误或重试耗尽，整次 Execution 进入 FAILED，停止后续分发，并按依赖能力尝试终止其他在途调用。正常业务输出，如 F-003 的“无法判断”，仍可参与汇聚。

为明确 WAITING_INPUT 与并行的关系，建议首期把用户澄清安排在并行段之前或汇聚之后。并行段内部请求澄清的配置在加载时提示不支持，动态出现该结果时按契约错误处理。此项属于新增的首期能力限制，需要用户判断。允许可选分支、部分成功或并行内澄清时，需要同时补充对应汇聚及等待规则。

#### M2-FINISH-06 · 循环与 Agent

建议循环配置明确循环体、进入条件、继续条件、退出去向及轮次上限。条件满足时执行一轮，循环体完成后再判定下一轮。初始条件不满足时允许零轮退出，后续输入映射应覆盖该路径。达到上限且仍需继续时进入 FAILED，保留明确的限制原因。

Agent 每轮产生行动建议或完成判断，Execution 检查工具允许范围、参数及剩余预算后，调用对应节点。行动结果交回后才进入下一轮。完成判断还须通过场景输出契约校验，才能形成最终结果。

建议配置每次 Agent 调用的轮次上限及每个 Execution 的工具调用总上限。一次成功取得的策略判断计一轮，每次实际工具调用尝试均计入工具调用总量，包括重试。循环中的 Agent 再次调用仍共享该执行的工具总量与剩余执行时间。

触顶后仍需行动、请求未允许的工具、行动参数或完成结果不符合契约，均以对应原因结束为 FAILED。场景已明确设计的业务澄清可进入 WAITING_INPUT。首期模型自我纠错次数或其他降级策略若需要支持，应另行确认。

#### M2-FINISH-07 · 重试与节点结果

建议由 Execution 根据场景规则统一决定一次节点运行的重试。M3、M4、M5 返回可识别的错误和调用信息，客户端或 SDK 的重试应计入同一预算，避免各层独立重试叠加。M6 提供参数约定与运行信号消费。

最大重试次数定义为首次尝试之后允许追加的次数，取 0 表示只尝试一次。仅对依赖明确标为暂时故障且允许安全重复的调用进行重试。参数错误、权限拒绝、配置错误及不满足输出契约默认直接失败。正常业务提示按场景结果处理。

每次重试保留逻辑节点运行的关联，并分配新的 invocationId。先前尝试超时后到达的结果按过期尝试处理。具有外部副作用的工具，只有在 M4 明确提供安全重试或幂等依据时才允许重试。

单次调用时限受该调用配置和 Execution 剩余时限共同约束。剩余执行时间耗尽时终止执行。重试计数达到上限、调用不可重试或后续分发已被终态禁止时，按相应错误收尾。正常业务结果已形成时，后续 SSE 传输失败保持已确定终态。

#### M2-FINISH-08 · 取消、并发和收尾

已有规则要求重复推进、重复结果、重复回复和会话收尾保持一致，终态后的迟到结果不再修改执行与会话。

建议对外取消请求携带目标 executionId，服务端校验它属于指定 Session 和可信调用身份，再操作该执行。延迟到达的旧取消请求保持对旧执行的关联。回复同时核对执行、当前追问及回复标识，相同回复标识携带不同内容时返回冲突提示。

终态及对应结果一起确定。收尾按同一执行关联更新可继承条件、最近结果和当前执行关联，对并发新调用呈现一致状态。收尾未完成时，新调用应先完成可重入收尾或返回忙时提示。旧执行重复收尾始终保持对该执行的关联。

完成、取消及超时竞争时，按核对截止时间后的第一次有效终态提交确定结果。客户端以服务端实际接受的状态为准，取消请求晚于已确定终态时返回已有状态。

分发前重新核对状态和调用是否已被认领。若发生取消与节点分发竞争，已被分发接受的调用按在途调用处理；取消之后停止接受新的分发。依赖实际停止能力仍需接入验证。

缓存读写故障导致状态无法可靠保存时，暂停新的节点分发并向调用方报告运行状态不可用。状态仍可读取时可重试事件处理或收尾，状态已经丢失时按既有会话失效规则处理。该规则不承诺进程崩溃后的可靠恢复。

#### M2-FINISH-03 · 缓存、结果与清理

建议“有效对话”指通过归属与状态校验后被接受的新输入或非重复关联回复。关联正确但信息仍不足的回复可以续期 Session，同时保留当前澄清的原截止时间。轮询、SSE 心跳、重复请求、节点后台活动和取消操作不延长会话有效期。Session 与当前 Execution 的有效期继续保持一致。

建议 F-002 在有效 Session 中保留当前未结束 Execution 的状态或追问，以及最近一次已结束 Execution 的结果或结束原因。开始下一次执行时仍可按原 executionId 获取上次结果；新的执行完成后替换最近终态结果。查询较早执行时明确返回结果已不可获取，避免把较新结果冒充请求的结果。读取结果时执行归属校验，且不延长缓存有效期。

建议 F-001、F-003 首期通过原调用传输结果，执行结束后释放一次性 Session。SSE 断开时执行仍按既有规则推进，若错过最终输出，调用方重新发起一次独立处理。是否为这两类场景提供短时结果补取，由用户明确取舍。

确认终态和必要的会话收尾结果后，释放节点中间数据与上传报告临时内容。在途调用仍使用的资源在调用返回或本地包装结束后清理；外部依赖实际停止情况单独验证。保留支持当前结果读取、回复去重和收尾幂等所需的最小记录，随结果替换或会话过期清理。旧结果替换后，当前执行标识及追问标识校验继续阻止旧事件作用于新执行。

缓存已过期或状态丢失时提示“会话已失效，请重新发起”，后续节点结果不得重新创建该会话。已有可用记录才能支持对原执行具体终态的判断。

### 三、运行参数

以下参数定义为建议。8 小时会话有效期来自已有说明书，其他数值留待用户确认及实际接入验证。

| 参数 | 计量与作用范围 | 达到限制或不合法时的处理 |
| --- | --- | --- |
| 执行时限 | 每个 Execution 累计 RUNNING 时间，正值 | 耗尽进入 FAILED |
| 澄清等待时限 | 每次进入 WAITING_INPUT 起计，正值 | 到期进入 FAILED |
| 单次依赖调用时限 | 每次模型、工具或知识调用的尝试，正值 | 产生调用超时，按可重试性及剩余执行预算处理 |
| 最大重试次数及间隔 | 每次逻辑节点运行，次数为非负整数，间隔为非负时长 | 达到次数上限后失败，间隔计入执行时限 |
| 循环轮次上限 | 每次进入 LOOP 的循环体运行次数，正整数 | 需要继续且已达上限时失败 |
| Agent 轮次上限 | 每次进入 Agent 的有效策略判断次数，正整数 | 需要下一轮且已达上限时失败 |
| 工具调用总上限 | 单个 Execution 内的全部工具调用尝试，正整数 | 后续工具调用所需预算不足时失败 |
| 会话空闲有效期 | 最近一次有效对话后 8 小时 | 会话失效，后续请求按失效处理 |

建议执行参数采用平台默认值、场景显式值及平台硬上限。场景显式值覆盖默认值，超出平台硬上限的配置校验失败。依赖调用参数允许场景节点显式覆盖，仍受硬上限与执行剩余预算限制。Execution 创建时保存本次有效值，后续配置变更对新执行生效。调用方输入和模型输出均不能自行放宽运行限制。

实施前每个必需参数应有明确数值、单位及来源；缺失时由已定义的默认值补齐，两者均缺失则场景不可调用。禁止把“未配置”自动解释为无限。具体配置格式和技术实现由实现设计确定。

### 四、验证场景与预期

每项验证记录前置状态、有效参数、输入与事件顺序、依赖返回、预期状态、节点调用次数、会话变化和可观察结果。下表验证编号为本任务局部编号。

| 编号 | 场景或事件 | 可检查的预期 | 依据 |
| --- | --- | --- | --- |
| V01 | 正常输入，依赖正常返回 | 按编排调用，最终 SUCCEEDED，收尾释放当前执行关联；F-002 更新可继承条件 | 已有 §4.2.3、§4.2.7 |
| V02 | 返回余额不足、暂无数据或无法判断条目 | 按业务规则输出，可正常 SUCCEEDED，技术错误另有失败原因 | 已有 §4.2.6 |
| V03 | 配置引用缺失；运行中条件无匹配且无默认分支 | 前者场景不可调用；后者 FAILED，无后续业务节点调用 | M2-FINISH-05 |
| V04 | RUNNING 无可运行节点、无在途调用及后续事件 | 以无法推进 FAILED，释放当前执行关联 | M2-FINISH-05 |
| V05 | 发出追问、重复回复、旧追问回复、信息不足回复 | 有效完整回复只续接一次并沿用版本；旧回复被拒绝；不足回复保留当前等待截止时间 | 已有 §4.2.3，加 01、08 |
| V06 | 执行时限耗尽；等待超时；续接后旧等待超时事件到达 | 前两者按适用时限 FAILED；旧等待事件失效；验证截止点前后事件处理 | M2-FINISH-01 |
| V07 | 可重试错误先失败后成功；持续失败；不可重试错误 | 依配置次数调用，重试标识可区分；持续失败耗尽后 FAILED；不可重试错误只有首次尝试 | M2-FINISH-07 |
| V08 | 首次尝试超时，重试开始后首次结果迟到 | 迟到结果不覆盖当前尝试，不触发额外后续节点 | M2-FINISH-07 |
| V09 | 并行乱序完成、重复结果、未选中路径 | 全部实际启动分支成功才汇聚一次，结果按分支标识关联 | M2-FINISH-02 |
| V10 | 必需并行分支失败，其他结果随后到达 | FAILED，停止后续分发，迟到结果保持终态及会话结果 | M2-FINISH-02 |
| V11 | 并行内部配置或动态返回澄清 | 分别在加载或运行时报告不支持，避免进入含在途并行调用的等待状态 | M2-FINISH-02 |
| V12 | 循环零轮退出、正常退出、到达上限仍需继续 | 前两者推进指定后继，上限场景 FAILED，后续轮次调用为零 | M2-FINISH-06 |
| V13 | Agent 正常完成、非法工具、轮次或工具预算耗尽 | 正常完成须满足输出契约；非法行动或预算耗尽失败，越界工具调用为零 | M2-FINISH-06 |
| V14 | 同一 Session 并发新调用、重复 next、重复收尾 | 最多一个未结束执行，同一次调用只认领一次，会话条件和当前关联一致 | 已有 §4.2.7，加 08 |
| V15 | 取消与完成竞争、旧取消到达新执行期间 | 只确定一次终态及对应结果；旧取消不能作用于新执行；迟到结果不推进 | 已有 §4.2.3，加 08 |
| V16 | 终态已确定，首次会话收尾失败，随后重试 | 只执行一次有效会话更新，新执行取得一致上下文，重复收尾保持结果 | M2-FINISH-08 |
| V17 | 缓存写失败、过期或重启丢失状态，随后收到旧结果 | 状态不能可靠保存时停止新分发；丢失时提示失效；旧结果不能重建会话 | 已有 §4.2.3，加 03、08 |

| V22 | 只轮询或发心跳；关联正确但信息不足的新回复 | 前者不能延长会话；后者可续期会话但保持该次等待截止时间 | M2-FINISH-01、03 |

后续先使用可控依赖返回和可控时间验证 M2 逻辑，再验证真实模型、工具、知识服务的错误分类、超时及取消能力。验证报告分别记录两类结果。业务扩展样例沿用 P-026，通用 M2 行为用例可复用相同检查约定。

### 五、调试观察要求

建议运行信号至少能关联 Session、Execution、场景版本、nodeId、invocationId，以及适用的分支、轮次和重试次数。记录启动校验结果、推进决定及等待原因、节点分发和结果接收、重复或迟到事件处理、超时及终态原因、会话收尾结果和资源清理结果。

从单个 executionId 应能回答目前处于什么状态、正在等待什么、为何调用或跳过某节点、哪项限制触发了结束、会话收尾是否完成。M2 提供这些事实，M6 细化记录器字段、存储与查询。真实调用终止效果、缓存故障行为及并发一致性均留待实现后验证。
