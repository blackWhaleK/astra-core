只记录本任务。建议、待确认与人的确认分别标注。

下文按讨论顺序保留来源记录。早期“追问返回即完成 Execution”的建议已被“F-002 追问保留原执行”的用户确认取代，当前取舍见[提案](proposal.md)。

## 2026-11-10 · 启动与 M2 首轮议题

- 输入事实与来源：BlackWhaleK 指定范围为“各模块设计思路及调整”。[说明书 V2](../../../docs/baseline/specificationV2.md)第 2.1、2.3 和 3.1 节给出 M2 职责、首期约束及 P-004—P-007，第 3.2 节规定 F-002 支持追问与选择，F-001、F-003 一次性处理。
- 问题与影响：F-002 等用户补充期间，M2 是继续保持同一次执行，还是结束当前执行并在下一轮新建？这会决定 M1 如何关联后续输入，以及 M2 何时释放运行资源。
- 方案与取舍：建议每轮新建执行，由短期上下文衔接查询条件及待选口径。同一次执行也可短暂挂起等待用户输入，但需要额外约定等待时限、取消和资源释放。
- 结论状态：待确认。
- 人工确认依据：未确认。
- 正文修订：无。
- 遗留问题：上下文保存位置与失效、SSE 断线处理、请求与执行的关联方式。

## 2026-11-10 · M1—M7 技术设计讨论安排

- 输入事实与来源：用户希望在总体架构和平台、业务功能清单基础上细化 M1—M7 的技术实现，先确定讨论顺序和深度。
- 问题与影响：M1 的接入行为依赖 M2 生命周期和 M3 输出契约，治理与基础设施的部分约束也会影响前期接口。
- 方案与取舍：按运行契约的依赖安排讨论。以 F-002 检验跨轮，用 F-001 校验一次性执行和工具调用，用 F-003 校验文档及检索边界。M6、M7 的横切约束随接口提前讨论，公共机制最后汇总。
- 结论状态：建议，见[任务提案](proposal.md)。
- 人工确认依据：未确认。
- 正文修订：无。
- 遗留问题：确认讨论安排和深度，再决定 F-002 的执行边界。

## 2026-11-10 · M2 编排方式与运行状态

- 输入事实与来源：用户要求比较 DAG、ReAct 和事件驱动，再结合 P-004—P-007 与 F-001—F-003 提出建议。首期支持短流程、受控 Agent，执行记录和会话不持久化。
- 方案与取舍：建议固定步骤采用 YAML 声明的无环流程。受控 Agent 可作为节点处理确需模型在运行时选择下一步的子任务。进度和治理信号可按事件发布，执行状态由 M2 管理。
- 状态讨论：分别表达 Execution 生命周期、Step 调度状态及业务结果。以 F-002 追问作为首个例子，讨论能否把需要补充条件视为本轮正常结束，并在下一次请求创建新执行。
- 结论状态：建议，待确认。
- 人工确认依据：未确认。
- 正文修订：无。
- 遗留问题：确认跨轮执行边界后，再定义取消、超时、并行汇聚及断线行为。

## 2026-11-10 · F-002 对话与单轮执行

- 输入事实与来源：用户指出 F-002 在同一个对话框内进行，提出“结束”应指对话结束。
- 方案与取舍：建议将用户可见的对话生命周期和 M2 单轮执行生命周期分别表达。系统返回追问或选项时，对话继续，前端等待输入。本轮执行可在返回结果后完成，后续回复沿用会话并创建新执行。
- 结论状态：用户已明确同一对话框内交互。执行是否跨轮及对话结束条件待确认。
- 人工确认依据：本轮用户说明 F-002 在同一个对话框内。
- 正文修订：无。
- 遗留问题：区分主动结束、离开页面和上下文过期，再明确会话的结束条件。

## 2026-11-10 · 按场景选择执行边界

- 用户判断：执行边界应由业务功能决定。F-001 每次独立请求新建 Execution。F-002 的 Execution 可以考虑随会话延续，以接续同一会话中的多条信息。
- 待讨论：跨轮信息由 Session 关联。Execution 可覆盖单轮、同一个查询目标的多轮，或整个会话。用补充口径、追问去年同期、切换到另一个指标三种输入检验边界。
- 确认状态：F-001 每次独立请求新建 Execution 已明确。F-002 的执行范围、等待与终止语义待确认。
- 正文修订：无。

## 2026-11-10 · F-002 查询完成后追查

- 人工确认依据：用户回复“同意 我也倾向于后者”，对应上一轮提出的 F-002 已返回查询结果后，用户问“去年同期呢？”的处理方式。
- 已确认：追查属于同一 Session 中的一次新查询，创建新的 Execution，可以沿用仍适用的前文条件。
- 待确认：当前查询返回追问或选项时，是否让原 Execution 进入等待并在收到回复后继续，以及等待超时、取消和换题的处理。
- 正文修订：无。

## 2026-11-10 · F-002 处理期间的输入限制

- 用户明确：会话处理消息、等待系统返回期间，用户不能输入。
- 简化建议：系统返回追问或选项后恢复输入，本次 Execution 完成，Session 保留待补条件。用户回复时新建 Execution，继续同一个查询目标。
- 待确认：追问返回后的 Execution 边界。
- 正文修订：无。

## 2026-11-10 · F-002 追问保留原执行

- 人工确认依据：用户明确“返回追问时不算完成本次执行，我认为这还是一个执行里”。
- 已确认：追问后用户补充条件或选择口径时，继续原 Execution。系统处理期间禁止输入，追问返回后恢复输入。查询完成后的追查在同一 Session 新建 Execution。
- 待确认：等待状态的命名，以及超时、取消和换题时的收尾规则。
- 正文修订：无。

## 2026-11-10 · F-002 换题关闭原查询

- 人工确认依据：用户明确“用户直接换题时，原查询可以关闭”。
- 已确认：等待补充期间，用户明确换题时关闭原查询。
- 关联执行边界：原 Execution 结束，新查询在同一 Session 新建 Execution。
- 待确认：关闭状态的名称、换题识别方式，以及等待超时和主动取消的处理。
- 正文修订：无。
