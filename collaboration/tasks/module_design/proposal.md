## 主动取消及断线收尾

主动取消、处理中断线及等待补充时离开页面的行为已获用户确认。取消与完成并发时的终态处理属于实现建议，外部调用可取消性和断线检测延迟待验证。

- 主动取消只结束当前 Execution，会话及此前有效的上下文继续保留。取消中的未完成结果标明中断，后续步骤停止推进。
- 处理中检测到响应连接异常断开时，采用同一取消机制，以断线作为关闭原因。查询已完成时保留其完成状态，避免晚到的取消或断线通知覆盖已确定的终态。
- 等待用户补充时离开页面，原查询继续等待，按已确认的会话 8 小时有效期管理。
- 已发出的外部调用能否中止需要按接口验证。M2 应停止新节点与重试，并丢弃取消后迟到的结果，防止其重新推进执行或覆盖新查询的上下文。
- 重连后先查询当前执行状态，再允许用户重新发起，避免连接恢复自动重复执行业务请求。
- Spring MVC 的断线检测依赖写入失败等信号，SSE 可通过心跳帮助检测。具体检测延迟及调用取消能力留待实现验证。[Spring MVC 异步请求文档](https://docs.spring.io/spring-framework/reference/6.2/web/webmvc/mvc-ann-async.html)
- Java 的任务取消支持尝试中断运行线程，实际停止仍依赖所执行任务的响应。外部调用取消需单独适配。[JDK 17 Future 文档](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/Future.html)

## Execution 状态及三种业务场景

依据 P-005、P-006、F-001—F-003 及本任务已确认的执行边界整理。用户已确认六种状态及其含义、适用场景。具体错误分类和并发终态处理仍待细化。本表覆盖已经开始处理的 Execution。

| 状态 | 含义 | 适用场景 |
| --- | --- | --- |
| RUNNING · 处理中 | 正在执行节点、等待模型或业务接口返回，或在允许范围内重试 | F-001、F-002、F-003 |
| WAITING_FOR_INPUT · 等待补充 | 已返回追问或选项，保留当前执行，等待用户补条件或选择口径 | F-002 |
| COMPLETED · 已完成 | 已形成本次最终业务结果，包括正常结果及按业务规则形成的说明或提示 | F-001、F-002、F-003 |
| FAILED · 已失败 | 解析、依赖调用或执行异常导致处理无法完成，必要的有限重试已耗尽 | F-001、F-002、F-003 |
| CANCELLED · 已取消 | 主动取消、处理中检测到异常断线，或等待时用户换题，导致当前执行关闭 | F-001、F-002、F-003，换题仅用于 F-002 等待补充期间 |
| EXPIRED · 已过期 | 等待补充时所属 Session 连续无交互 8 小时过期，当前执行随之关闭 | F-002 |

COMPLETED、FAILED、CANCELLED、EXPIRED 为执行终态。实现上建议 M2 接受取消并阻止后续推进后进入 CANCELLED，尝试中止在途调用，迟到结果退出处理。外部调用的实际中止能力待验证。

| 当前状态 | 发生的事情 | 转换与后续行为 |
| --- | --- | --- |
| 新任务开始 | 接受一次独立业务处理 | 创建 Execution 并进入 RUNNING |
| RUNNING | 需要用户补条件或选择口径 | 原执行进入 WAITING_FOR_INPUT，恢复输入 |
| WAITING_FOR_INPUT | 用户回复，继续原查询 | 原执行进入 RUNNING，处理期间禁用输入 |
| RUNNING | 形成最终业务结果 | 进入 COMPLETED |
| RUNNING | 发生导致任务无法完成的错误，必要重试耗尽 | 进入 FAILED，返回对应错误提示 |
| RUNNING 或 WAITING_FOR_INPUT | 用户主动取消 | 进入 CANCELLED，有关联 Session 时继续保留会话 |
| RUNNING | 服务端检测到处理中连接异常断开 | 进入 CANCELLED，记录断线原因；已有会话继续保留 |
| WAITING_FOR_INPUT | 用户明确换题 | 原执行进入 CANCELLED，同一 Session 新建 Execution 处理新查询 |
| WAITING_FOR_INPUT | 用户离开页面 | 保持等待，沿用会话空闲有效期 |
| WAITING_FOR_INPUT | 所属会话连续无交互 8 小时过期 | 进入 EXPIRED，释放相关临时上下文 |

| 场景 | 执行边界与典型路径 | 业务结果示例 |
| --- | --- | --- |
| F-001 辅助办理人力业务流程 | 每次独立请求创建一个 Execution，RUNNING → COMPLETED。异常或取消时进入相应终态 | 返回页面 JSON，或返回余额不足、信息不足等业务提示，均可归入 COMPLETED |
| F-002 查询与分析人力数据 | 一次查询可跨多轮，RUNNING ↔ WAITING_FOR_INPUT，最终进入 COMPLETED。同一 Session 中后续追查新建 Execution | 返回查询分析或暂无数据、无法确定指标口径等最终说明，可归入 COMPLETED。补条件或选口径属于等待 |
| F-003 检查征信报告内容 | 按一次性处理范围，每次提交报告分析创建一个 Execution，RUNNING → COMPLETED。再次上传重新分析时新建执行 | 返回满足、不满足或无法判断的检查结论，可归入 COMPLETED。Word 解析失败建议归入 FAILED，给出重新上传提示 |

F-001 和 F-003 按既定一次性处理范围返回结果或提示。F-003 缺少判断依据时，在本次结果中说明无法判断。

等待用户输入的 8 小时规则与运行中模型、工具调用的超时分别管理。运行中的调用超时按有限重试和失败规则处理，具体时长待定。一次节点重试仍属于原 Execution。

建议终态一经确定便保持，晚到的完成、取消或断线通知按当前终态处理。用户重新发起任务时新建 Execution，可从仍有效的 Session 获取适用上下文。已完成执行所属会话后来过期时，清理上下文，执行的完成结论保持。

## F-001 与 F-003 采用 Execution 模型（本轮提案，待确认）

F-002 的简化方向已获用户接受。本轮建议将 Execution 生命周期与任务上下文的模型用于 F-001、F-003。已有处理职责保留为内部流程节点，重试、取消、输入输出与并行汇聚由运行过程管理。

| 场景 | 一个 Execution 的范围 | 生命周期状态 | 主要临时上下文 |
| --- | --- | --- | --- |
| F-001 | 一次独立业务意图处理，最终返回页面数据或业务提示 | RUNNING、COMPLETED、FAILED、CANCELLED | 用户文本、可信身份、意图、业务参数、人员查询结果、余额和最终输出 |
| F-002 | 一次查询或分析，可跨多轮补充，完成后的追查新建执行 | 六种已确认状态 | 当前查询条件、口径、待补信息，关联 Session |
| F-003 | 一次上传报告的检查任务，再次上传重新分析时新建执行 | RUNNING、COMPLETED、FAILED、CANCELLED | 当次报告、解析内容、制度依据、检查项及检查结果 |

F-001、F-003 使用单次请求上下文，按当前范围一次性返回。运行中的调用超时遵循各自的有限重试与失败规则。8 小时会话空闲过期规则用于 F-002 的会话及其中等待补充的查询。

### F-001 内部流程与结果

理解请求与提取参数 → 校验并选择分支 → 按需查询人员和余额 → 判断业务条件 → 组装页面 JSON 或提示。

- 本人请假使用可信身份关联本人，校验后查询本人余额，再比较模型分析出的请假天数。
- 为他人请假先查询被请假人，唯一匹配后查询其余额，再判断条件。输出按基线仅在请假字段中增加姓名。
- 补卡按单日期规则校验后组装结果。
- 余额不足、信息不足、人员无匹配或多匹配、日期需要提醒等情况，形成约定业务提示后进入 COMPLETED。
- 必要的人员或余额调用失败并耗尽重试时进入 FAILED，返回“系统异常，请稍后”。
- 主动取消或处理中检测到异常断线时进入 CANCELLED，停止后续推进并处理迟到结果。

一个 Execution 内的业务判断与调用返回决定流程走向。业务提示提前返回时结束本次处理。用户修改文本重新提交时创建新 Execution。

### F-003 内部流程与结果

解析 Word → 检索适用制度 → 整理检查项与对应报告内容 → 按项检查 → 汇总总体意见、逐项结论和修改建议 → 组织页面文字与表格。

- 文档解析提取文本、结构及可用内容定位，沿用无固定模板的输入范围。
- 检索得到适用制度及条款依据，检查项关联制度要求和报告内容。缺少明确要求的内容时记录缺项。
- 分项检查输出满足要求、不满足要求或无法判断。缺少制度要求的报告内容可判为不满足要求，判断依据不足时说明无法判断及原因。
- 找不到适用制度或无法确定适用依据时，形成制度依据不明确的说明并进入 COMPLETED。
- 所需检查结束且汇总结果形成后进入 COMPLETED，结果可以包含不满足要求或无法判断。
- Word 解析失败时进入 FAILED，并提示检查文件后重新上传。知识库或模型的必要调用重试耗尽时进入 FAILED，返回系统异常提示。
- 主动取消或处理中检测到异常断线时进入 CANCELLED。当次报告及解析内容按临时资源规则清理，清理时点及状态查询接口待细化。

### F-003 分段与并行

需要分段时，运行过程按检查项关联相关报告片段与制度依据。独立检查项可并行处理，存在依赖的内容按顺序处理。Execution 在处理和汇总期间保持 RUNNING。

并行运行过程保留必要的任务关联、完成结果及错误信息，汇总时按检查项归集。此信息作为当次运行的内部数据。对外仍通过 Execution 管理生命周期。

用户已确认必需分项的技术调用失败且重试耗尽时，整体进入 FAILED，停止其余未完成工作并忽略迟到结果。业务上的无法判断可作为正常检查结论进入汇总。部分技术失败后交付部分报告的模式待有明确需求再讨论。

### 对独立 Step 模型的调整

本轮建议三种场景统一采用 Execution 作为生命周期对象，流程节点继续承担处理职责，独立 Step 对象与其状态机从首期候选模型中移除。F-001 的既有业务步骤和执行效果继续作为流程依据。F-003 的内部并行控制、有限重试和追踪信息仍需实现，具体契约待设计。

## F-001 前一轮独立 Step 方案（已确认流程的来源，本轮重评对象模型）

本节保留此前确认的流程划分及 Step 方案。上文提出将流程职责保留、生命周期统一到 Execution 的调整，待用户审阅。

Execution 对应一次业务任务，Step 对应该任务内一次可独立调度、记录结果及控制重试的节点执行。YAML 中的节点提供步骤定义，执行时创建属于当前 Execution 的 Step。同一节点被不同任务或不同轮次调用时，各自形成 Step。针对同一次节点调用的重试，保留 Step 并增加尝试次数。

用户已确认 F-001 按六个逻辑步骤组织。意图识别、字段提取及请假时段和天数分析先合并为一次模型处理，输出意图、业务参数及需要提醒的情况。具体调用效果待验证。

| 步骤 | 处理方式 | 职责与结果 |
| --- | --- | --- |
| 理解请求 | 模型处理 | 识别本人请假、为他人请假或补卡，提取字段。请假时段与天数仍按基线由模型分析。无法识别意图时形成对应提示 |
| 校验与分流 | 代码校验及条件分支 | 校验字段完整性、类型与约定格式，按现有业务规则处理日期有效性及模型返回的提醒。补卡走单日期校验，合法时进入结果组装；请假继续相应查询路径 |
| 查询被请假人 | 业务工具，仅为他人请假 | 按原系统授权查询人员。唯一匹配后供余额查询使用，无匹配或多匹配时返回信息不足提示 |
| 查询余额 | 业务工具，两类请假 | 本人请假使用可信身份关联本人，为他人请假使用上一步确定的人员，取得请假余额 |
| 判断余额 | 代码处理，两类请假 | 比较分析出的请假天数和余额，得到满足条件或余额不足的结论 |
| 组装结果 | 代码处理，所有正常业务出口 | 生成已约定页面 JSON 或业务提示。为他人请假的输出仍按基线仅增加姓名。M1 负责对外传输和展示 |

路径按既有业务规则连接。补卡通过校验后直接组装结果，本人请假通过校验后查询本人余额，为他人请假先确定人员再查询其余额。意图不明、信息不足、休息时间等需提醒的情况，以及余额不足，均走对应业务提示出口并完成本次任务。

### 已确认的 Step 状态

| 状态 | 含义 |
| --- | --- |
| PENDING | 已登记，等待依赖满足或被调度 |
| RUNNING | 正在执行，包括在预算内等待下一次重试 |
| COMPLETED | 本步骤已产生符合契约的结果，供后续选择路径或组装输出 |
| FAILED | 本步骤发生技术错误，且已不可重试或耗尽重试预算 |
| SKIPPED | 已确定本次路径无需执行此步骤，如补卡分支的余额查询 |
| CANCELLED | 因主动取消、断线或上游失败等原因，正在执行或尚未执行的步骤被终止 |

每个 Step 关联 executionId、stepId、节点定义引用、当前状态、输入输出及尝试次数。错误原因、耗时等细节在契约设计时补齐。

### Step 对 Execution 的影响

| 情况 | Step 行为 | Execution 行为 |
| --- | --- | --- |
| 步骤完成，但仍有后续步骤 | 该步骤进入 COMPLETED | 保持 RUNNING，按依赖调度后续步骤 |
| 查询到余额不足或人员无匹配 | 查询或判断步骤进入 COMPLETED，结果包含业务结论 | 走提示出口，组装结果后进入 COMPLETED |
| 工具调用发生可重试错误 | 保持 RUNNING，在同一个 Step 增加尝试次数，保存每次错误 | 保持 RUNNING，后续依赖步骤继续等待 |
| 必需步骤失败，重试耗尽或不可重试 | 失败步骤进入 FAILED，剩余待执行步骤按上游失败原因取消 | F-001 进入 FAILED，由统一错误处理返回提示 |
| 用户取消或处理中异常断线 | 正在执行及未执行步骤取消，已完成或已跳过步骤保留原状态。迟到结果退出处理 | 按已确认规则进入 CANCELLED |
| 分支未被选择，或业务提示提前结束路径 | 已确定无需执行的步骤进入 SKIPPED | 根据选中路径继续，形成最终结果后进入 COMPLETED |

在 F-001 中，整体完成取决于选中路径的必需步骤以及最终结果是否已形成。一次工具重试只重做该工具步骤，重试范围限于当前调用，避免重新识别意图或重跑整个任务。人员与余额查询的重试上限沿用可配置要求，具体次数待定。

本节先覆盖 F-001。F-002 跨轮时的步骤衔接、F-003 并行步骤的汇聚与失败规则作为下一轮对照议题。

建议接下来先用 F-002 的“查询今年离职率 → 选择正式员工口径 → 返回结果”梳理每轮 Step、等待位置和条件传递，再讨论 F-003 并行汇聚。之后统一细化临时上下文的内容、存放和清理，最后将运行规则落实到 YAML 节点契约。

## F-002 简化为 Execution 状态与查询上下文（已确认方向）

用户接受 F-002 由 Execution 管理任务生命周期、查询上下文支持跨轮接续的简化方向。流程节点承担内部处理职责，独立 Step 对象和状态机由该方案替代。

Execution 状态表达整次查询是否处理中、等待补充或已经结束。节点状态表达每个处理环节的调度情况。F-002 当前围绕条件补充和一次查询推进，尚未提出逐节点独立管理的使用需求，可用更小的运行模型覆盖这些行为。

| Execution 状态 | 进入条件 | 后续行为 |
| --- | --- | --- |
| RUNNING | 新建查询任务，或用户补充同一查询 | 理解输入、检索口径、校验条件，条件齐全后取数、分析并组织响应。处理中禁用输入，停止操作可用 |
| WAITING_FOR_INPUT | 返回追问或口径选项 | 保存当前查询条件、候选口径和待补内容，允许用户输入 |
| COMPLETED | 已形成最终结果或业务说明，如暂无数据、无法确定口径 | 结束本次查询，后续追查在同一会话创建新 Execution |
| FAILED | 技术错误导致无法完成，且必要重试已经耗尽 | 结束本次查询并返回对应提示 |
| CANCELLED | 用户主动取消、等待时明确换题，或处理中检测到异常断线 | 关闭当前执行，停止后续推进，保留已有会话 |
| EXPIRED | 等待补充时会话连续无交互 8 小时过期 | 关闭当前执行并释放相关临时上下文 |

### 保留的信息与处理职责

- Session 继续关联对话、适用历史信息和当前 Execution。
- Execution 保存标识、状态、当前查询目标、已确定条件、口径依据、待选项、待补内容及最终结果或结束原因。
- 理解输入、检索口径、校验条件、查询数据、分析数据、组织响应作为内部处理环节，由当前条件决定后续路径。调用的临时返回值、重试次数及追踪信息由运行过程管理。
- 需要追问时保存查询上下文，Execution 进入 WAITING_FOR_INPUT。用户补充后，原 Execution 回到 RUNNING，从条件理解和校验继续，适用的口径结果可复用，受修改影响的条件与结果重新校验。
- 对调用方提供围绕 Execution 的发起、补充、取消和状态查询能力。节点失败、重试、分支选择及结果汇总在 M2 内部完成。
- 内部重试仍需限定次数，取消后仍需阻止后续推进和迟到结果污染上下文。这些控制可以通过调用返回、执行上下文和取消标记实现，具体实现待设计。

该方案移除 F-002 独立 Step 对象及其第二套生命周期，保留流程节点及必要的运行信息。此前节点职责划分可继续用于描述流程。F-001 及 F-003 的统一模型见本轮提案。

示例中，提出“查今年离职率”创建 Execution A；返回口径选项后 A 等待；回复“正式员工”后更新 A 的查询条件并继续；返回结果后 A 完成；再问“去年同期呢”创建 Execution B。这个过程可由执行状态和查询上下文接续。

## F-002 前一轮分步方案（对比参考，已由简化方向替代）

以下保留前一轮独立 Step 方案作为讨论来源。当前采用前述 Execution 简化方向，Execution 的跨轮边界沿用已确认结论。

### 六类逻辑步骤

| 步骤 | 职责 | 主要输出 |
| --- | --- | --- |
| 理解本轮输入 | 结合本轮消息、当前待补内容和会话中的适用信息，识别指标、时间、范围和分析要求。用户明确修正的条件覆盖原值 | 本轮条件变更及与当前任务的关系 |
| 检索指标口径 | 调用 M5 获取指标定义、统计口径和适用依据。多口径时提供候选，复用既有检索结果时核对适用性 | 有依据的候选口径及引用，或口径缺失结果 |
| 校验查询条件 | 对照口径与业务接口要求，检查条件完整性和选择有效性，决定追问、取数或返回最终说明 | 可执行查询条件，或缺项、待选项、口径缺失说明 |
| 查询数据 | 通过 M4 调用原系统接口，传递可信身份和已校验条件。对比分析可包含多次必要取数 | 数据、单位、对应条件，或无数据结果 |
| 分析数据 | 依据口径及实际数据组织描述、趋势或对比分析，原因判断必须有数据依据 | 分析内容及其依据，数据不足时的说明 |
| 组织响应 | 将上游结果组织为追问、口径选项、文字、表格或柱状图数据，再由 M1 对外呈现 | 带响应类型的内容，明确需要补充还是形成最终结果 |

校验后需要补充时直接组织追问或选项；条件齐全时取数、分析、组织最终结果；找不到口径时组织最终说明。取数返回无数据时直接组织暂无数据提示。满足所需数据条件时才开展相应分析。

### 追问和继续执行

- 组织追问的 Step 形成输出后进入 COMPLETED，Execution 进入 WAITING_FOR_INPUT。已登记但尚待条件的取数和分析步骤保持 PENDING。
- 等待期间保存当前任务的查询条件、候选口径、缺项和待执行信息，释放本轮处理资源。保留期沿用会话连续无交互 8 小时规则。
- 用户补充同一查询时，原 Execution 回到 RUNNING。为本轮输入创建新的理解和校验 Step，继续使用适用的口径依据；口径或相关条件变化时重新检索或校验。
- 同一逻辑节点再次处理新消息时创建新的 Step 实例，旧的已完成实例保留原状态。当前工具调用的技术重试仍留在原 Step，增加尝试次数。
- 条件仍不完整或选择无效时，再创建响应 Step 返回追问，原 Execution 继续等待。条件齐全后才调度取数和分析。
- 最终响应形成后，其 Step 进入 COMPLETED，Execution 进入 COMPLETED。等待时明确换题则关闭原执行，新查询使用新 Execution。

### 示例

例子仅用于解释调度。假设其他必填查询范围已经明确，尚需在全员和正式员工口径之间选择。

| 交互 | Step 调度 | Execution 状态 |
| --- | --- | --- |
| 用户提出“查今年的离职率” | 理解输入 → 检索口径 → 校验条件 → 组织口径选项，各实际执行的 Step 完成 | Execution A 从 RUNNING 进入 WAITING_FOR_INPUT |
| 用户回复“正式员工” | 新的理解和校验 Step 接收补充，核对口径后执行取数、分析及新的响应 Step | A 回到 RUNNING，形成最终结果后进入 COMPLETED |
| 结果后用户问“去年同期呢” | 从同一会话提取仍适用的指标和口径，重新校验时间条件并执行查询 | 新建 Execution B，A 保持 COMPLETED |

### 上下文与状态归属

| 对象 | 建议保存的临时信息 |
| --- | --- |
| Session | 对话消息及适用的历史查询信息、当前 Execution 关联、会话空闲有效期 |
| Execution | 当前任务目标、已确定条件、候选和已选口径、待补内容、执行位置及步骤结果 |
| Step | 本次节点调用的输入、输出、状态、尝试次数及错误 |

Step 就绪时使用当前已校验的执行参数。后续明确修正条件时重新校验受影响的结果，避免使用旧条件对应的产物。可信身份由接入侧提供并沿调用链传递，查询文字用于业务条件解释。

跨轮重新进入由 M2 调度。每轮处理可表达为一个有限的分支流程，Execution 连接多轮。跨轮行为需要在 YAML 节点契约中显式描述，具体语法待设计。

依赖调用失败按已有有限重试规则处理，必要步骤最终失败时 Execution 进入 FAILED。口径缺失、无数据或依据不足属于业务结果，形成最终说明后进入 COMPLETED。取消、断线及会话过期沿用已确认规则。会话过期时等待的 Execution 进入 EXPIRED，已登记未执行的 Step 可按会话过期原因进入 CANCELLED，此 Step 映射待确认。
